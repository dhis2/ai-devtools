# ADR-0001: Updates to dhis2-apps bootstrapping skill

## Status

Accepted

## Context

The `skill-dhis2-apps` bootstrapping reference was derived from the main DHIS2 app
platform skill. Several instructions in the guide were out of step with the actual
`react-router` template scaffolded by `pnpm create @dhis2/app --template react-router`,
discovered by inspecting the template source at
`packages/create-app/templates/template-ts-dataelements-react-router/`.

Issues found:

1. **Redundant steps** — the guide told the AI to create files from scratch that the
   template already generates: `tsconfig.json` (with `@/*` paths), `viteConfigExtensions.mts`
   (with the Vite `@` alias), and `d2.config.js` (with `type`, `entryPoints`,
   `viteConfigExtensions`).

2. **Inconsistent `jsx` override** — Step 6 set `"jsx": "react-jsx"` in `tsconfig.json`
   (the automatic transform, which means no `import React` needed), but the App.tsx
   example in Step 8 imported React anyway. The template uses `"jsx": "react"` and
   imports React explicitly throughout.

3. **Pinned TanStack Query v4** — Step 3 pinned `@tanstack/react-query@4` with a
   comment explicitly blocking v5, which is now the current major.

4. **Too many mid-process questions** — the guide asked about DHIS2 API version, ESLint
   config preference, and whether a setup step was needed, interrupting the flow at
   multiple points.

5. **Missing common utilities** — `date-fns` and `classnames` were not installed during
   bootstrapping despite being used in almost every app.

6. **ESLint `import/named` false positives** — after a real bootstrapping run, ESLint
   reported errors like `QueryClient not found in '@tanstack/react-query'` and
   `Outlet not found in 'react-router-dom'`. These are false positives caused by the
   ESLint import plugin using Node's CommonJS resolver, which cannot follow TypeScript
   re-exports (`export * from '...'`). The fix — `eslint-import-resolver-typescript` —
   was already documented in the skill's troubleshooting table but was not applied
   proactively during bootstrapping. This was also fixed upstream in both
   `create-app` templates (see `cli` repo ADR-0001).

## Decision

- **Remove old Steps 5 and 6** (create `vite.config.mts` and add tsconfig paths). The
  template already provides both. Step 4 is updated to only change the two fields that
  need updating: `name` and the entry point path (`AppWrapper.tsx` → `App.tsx`).

- **Drop the `jsx` override**. Keep the template's `"jsx": "react"` as-is. Remove
  `import React from 'react'` from the App.tsx example to be consistent with not
  overriding it (the template already handles JSX correctly at the Vite build level).

- **Use unpinned `@tanstack/react-query`** (latest, currently v5). Update the
  `useApiDataQuery` wrapper generics to match v5's simplified type signatures.

- **Single upfront confirmation** — gather the app name and present a full plan summary
  before any commands run. The user confirms once; no further questions during the
  process. API version defaults to latest (v43), ESLint/Prettier defaults to DHIS2
  shared configs.

- **Install `date-fns` and `classnames`** in Step 3 alongside the rest of the stack.

- **Add `eslint-import-resolver-typescript`** to the ESLint install step, wire it into
  `eslint.config.mjs` via the `settings['import/resolver']` block, and run
  `pnpm eslint --fix` after setup to auto-correct import ordering in scaffolded files.
  The same fix was applied upstream to both `create-app` templates so future scaffolds
  won't need this step at all.

## Consequences

- Steps renumbered: 8 steps total (was 10) — two fewer steps for the AI to execute.
- `AppWrapper.tsx` (generated by template) should be deleted after Step 6, since its
  role is absorbed into `App.tsx`.
- `viteConfigExtensions.mts` filename is kept as the template generates it; `d2.config.js`
  references it by that name.
- Any future update to the `react-router` template should be re-checked against these
  steps to ensure they stay in sync.
